Integration engine for healthcare

An integration engine that tells you why the queue is stuck.

Ductus moves HL7 v2, JSON, XML, CSV and files between hospital systems. Interfaces are TypeScript you can read, test and keep in Git. They run on one Rust binary with PostgreSQL as the store and queue.

It's for interface teams running hundreds of Mirth or Cloverleaf connections who are tired of guessing.

Early development. v0.5 is in progress and Ductus isn't ready for production yet. Everything on this page works today and is checked by tests or a demo that runs on every change.

What an interface looks like

A folder with config, code and a test

No drag-and-drop canvas and no exported XML. An interface is a few small files that diff cleanly in a pull request and run the same way on your laptop as in production.

interfaces/adt-in/interface.yaml
name: adt-in
source:
  mllp: { port: 6661 }
script: transform.ts
ordering:
  key: PID-3.1      # same MRN stays in order
retention: 3w
destinations:       # each: own queue, retries, status
  lab:
    mllp: { host: 10.0.0.5, port: 6662 }
  billing:
    http: { url: "https://billing.example.org/charges" }
    transform: toBilling
    output: json
interfaces/adt-in/transform.ts
import { db, kill, type Message, type Meta } from "@ductus/sdk";

export function transform(msg: Message) {
  if (msg.MSH[9][1] !== "ADT") return null;   // filter
  msg.PID[5][1] = msg.PID[5][1].toUpperCase();
PID-5 Patient Name (XPN)
  return msg;
}

export async function toBilling(msg: Message, meta: Meta) {
  const account = await db("billing_db").one(
    "SELECT id FROM accounts WHERE mrn = $1", [msg.PID[3][1]]);
  if (!account) return kill("not billable");
  return { id: meta.id, account: account.id, event: msg.MSH[9][2] };
}

HL7 the way you say it

msg.PID[5][1] is PID-5.1, numbered like the spec. Hover it in VS Code and you see the field's name and data type. A missing field reads as empty instead of throwing.

Tests without production

ductus test runs each interface's tests with databases and APIs mocked in one line (mock.db("billing_db", [{ id: 42 }])). Forget a mock and the failure names the line to add.

Checked before deploy

ductus validate type-checks the code with an embedded TypeScript compiler and checks every database and API name it uses against the environment you're promoting to.

What it fixes

The annoyances you've learned to live with

Each of these comes from years of running interface engines at hospital scale. Each one names how we prove the fix.

When something goes wrong

“The queue is stuck.”The count goes up. Someone scrolls to the first message and guesses whether the receiver is down or rejecting one patient. A busy patient looks the same as an outage.

ductus hotspots shows where each backlog sits and what it means: one message holding up a worker, a receiver that's down, or one patient arriving faster than a receiver takes them. It names the message, the MRN, the attempts and the last error.

The hotspots demo above runs on every change. 300,000 waiting messages are analysed in about 40 ms.

One receiver down holds up the rest.Or it errors, and someone works out by hand which systems got which messages and resends to the one that missed them.

Each destination of an interface has its own queue, order, retries and status. A receiver that's down holds up only itself, then catches up in order. Status is one small row per message and destination, with no extra copy of the message.

Lab down while billing and archive get all 200 messages. Engine killed with 200 waiting, restarted, lab back: 200 of 200 delivered, none twice, none out of order.

One endless loop hangs the engine.A runaway transformer script blocks its channel and everything that shares its process until someone notices.

Every run of interface code has a time budget and every script engine a memory limit. Runaway code is stopped, its message is set aside with a plain reason, and the neighbours keep flowing. If it keeps happening, only that interface stops, and its messages wait safely.

Four interfaces on one thread: three loop or fill their memory, the fourth still delivers 200 of 200, and every sender is acknowledged at full speed.

A receiver cut off for months fills the disk.After a vendor's breach, its feed waits until security clears it. Either the backlog is purged with everything else, or nothing old can be purged while it waits.

Old messages go by dropping whole partitions, never by a pruner deleting rows under live traffic. Messages someone still needs move aside to a held area first. The disk holds the normal window plus the backlog, and the backlog is still delivered in order.

300,000 held messages moved in the background in 58 seconds, then delivered in order in 174 seconds once the receiver was resumed.

Maintenance means juggling threads.Stop inbound one by one, watch the outbound queues drain, stop the engine, and hope nothing arrived in between.

ductus drain --wait --stop stops taking messages on every interface at once, so senders keep theirs queued. It delivers what's stored, shows what it's waiting for, and stops the engine once nothing is pending.

An end-to-end test drains with three messages waiting for a receiver that's down, and the engine exits only after all three are delivered.

Knowing what connects to what

“Vendor X was breached. Which interfaces?”The answer lives in people's heads, an old spreadsheet, or a grep through exported channels that misses the lookups buried in scripts.

Every interface names the applications and vendors on each side. ductus impact --vendor "Epic Systems", or --host 10.20.30.0/24 for a VPN change, lists every interface affected, how it's affected, and who owns it. That includes databases its code queries, found through shared libraries.

Tested with a vendor reached only through a database that a shared library queries.

“The new connection doesn't work.”Is it DNS, the firewall, the VPN, their certificate or the password? Each guess is a ticket and a day.

ductus doctor checks every connection from the server it runs on: DNS, TCP with the source address, TLS certificates and expiry, then each system's own login. A failure says what it means, for example “nothing answered: firewall request from 10.1.2.3 to 203.0.113.7 port 443 (TCP)”.

Tests for refused and unresolvable hosts, untrusted certificates, refused tokens and wrong database passwords.

Passwords and tokens copied into scripts.They end up in many channels, get logged by accident, and are painful to rotate.

Databases, SFTP servers and APIs are named once per environment, and secrets are stored encrypted. Code calls api("empi").get("/patients/1") and the engine adds the token outside the script. Rotating a token means changing one secret.

Interface code has no network or file access of its own. The engine refuses anything else.

Files

A big file crashes the engine halfway.Then nobody knows which rows went through. Resend everything and get duplicates, or hand-edit the file.

Files are streamed record by record. Every 500 records are committed together with the position in the file. After a crash, reading resumes there. A file is only picked up once it has stopped changing, and only moved once everything in it is stored.

Engine killed partway through a 300,000-row file and restarted: 300,000 stored, 0 duplicates.

Guarantees

What it promises, and how that's checked

Every guarantee has an end-to-end demo that kills the engine mid-stream and checks the result. They all run on every change.

Stored before acknowledged

A message is committed to PostgreSQL before the sender gets its ACK. Files are moved only after every record is stored. An engine crash loses nothing.

In order per patient

Messages with the same key, such as the MRN, reach each destination in order, across restarts. Different patients go in parallel.

At least once, with a stable id

A crash between sending and recording it can resend one message. Dedupe at intake and a stable id per message let receivers ignore the repeat.

Rollback is reinstalling

Database changes only ever add, and older versions start on newer schemas. Rolling back means reinstalling the previous binary.
